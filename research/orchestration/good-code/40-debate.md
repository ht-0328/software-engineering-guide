## 論点と決着

### D-1 名前の長さを、条件つきで書くか一律で書くか

| 者 | 立場 | 理由 | 根拠 |
|---|---|---|---|
| Claude | 見落とし | 両者は対立ではない。`B-41` だけが「識別子が見えるコードの行数」という条件を持ち、その条件を落として並べたことが誤りである | `B-41`、`B-43`（ともに一次資料）、`W-4`、`W-27`（二次資料） |
| Antigravity | 見落とし | スコープの広狭という適用条件の違いを見落としている。局所変数では短い名前を許し、業務ロジックと公開APIでは1文字名と略語を避ける、という使い分けで書くべきである | `B-41`、`B-43`、`A-23`、`W-4`、`W-27` |

**決着**: 条件つきで書く。スコープの広さで基準を変える。`B-41`（`SRC-CODE-001` p.44）は「その名前が見えるコードの行数」を明示した条件つきの主張であり、`B-43`（`SRC-DESIGN-001` p.17-18）は業務アプリケーションのフィールドと引数を対象にした主張である。**対象が違うため、そもそも対立していない。** `W-4`（Google: 十分に伝わる長さで、読みにくくなるほど長くない）と `W-27`（公開メソッドに1文字引数を使わない）は、同じ規則を別の言い方で述べたものである。

**最終文書での扱い**: 観点として書く。「スコープが数行なら短くてよい。フィールド・引数・公開メソッドでは完全な単語を使う」という形にする。行数の閾値は置かない。

### D-2 循環的複雑度の数値をどう書くか

| 者 | 立場 | 理由 | 根拠 |
|---|---|---|---|
| Claude | 反対 | バグ混入確率の数値は書籍が MathWorks 社の目安の引用であると脚注で明示しており、測定条件が無い。一方 NIST は一次資料でありながら数値そのものを controversial と述べている | `B-8`、`W-9`、`W-11`、`W-12` |
| Antigravity | 見落とし | 書籍側の確率は測定条件の裏づけが無い引用に過ぎず、NIST の「10に抑えるか理由を文書化する」運用方針を見落としている。NIST を主軸に書くべきである | `B-8`、`A-6`、`A-19`、`W-9`、`W-10`、`W-11` |

**決着**: NIST SP 500-235 の運用方針を主軸にする。**バグ混入確率の表（25%、40%、70%、98%）は書かない。**

理由は3つある。第1に、`B-8`（`SRC-CODE-002` p.354）は脚注9・脚注10で「MathWorks 社の目安を採用した」「目安は指標がいくつかある」と自ら断っており、書籍の本文としては一次資料だが、確率の値については二次資料である。第2に、`A-6` と `A-19` は同じ表を読んだものであり、**同じ資料を読んだ2者の一致は2票にならない。** 第3に、`W-9` から `W-12`（NIST SP 500-235、1996年）は規格化団体の一次資料でありながら、上限の数値そのものを controversial と述べている。より強い資料が自ら不確かさを述べているものを、より弱い資料の確率で上書きしてはならない。

**最終文書での扱い**: 「10」は目安として書く。合否の基準としては書かない。運用は `W-11` の形（10に抑えるか、超えた理由を残すか）で書く。`W-13`（複雑度90のモジュールに何もしない10分岐を足して「修正複雑度10」に見せた実例）を、指標を目標にしたときに起きることの証拠として添える。

### D-3 メソッドとクラスの行数の上限を書くか

| 者 | 立場 | 理由 | 根拠 |
|---|---|---|---|
| Claude | 反対 | メソッド10行・クラス100行の裏づけは Ruby の道具の既定値と著者の現場経験であって測定ではない。合否の基準に見える形で書くと `docs/index.md` の「数値は目安として書く」に反する | `B-7`、`B-2`、`B-23` |
| Antigravity | 反対 | 提示された数値は著者の経験則による一例に過ぎず、行数の短縮より理解時間の短縮が優先されるべきである | `B-2`、`B-7`、`A-3`、`W-17` |

**決着**: 一律の数値基準として書かない。2者が同じ結論に達しており、根拠も一次資料である `B-2`（`SRC-CODE-001` p.25、p.110「行数を短くするよりも、他の人が理解するのにかかる時間を短くする」）に基づく。`B-7` は `SRC-CODE-002` の脚注7に「筆者は C 言語、C++、C#、JavaScript、Ruby などを現場で経験してきました」とあり、**測定ではなく経験である。**

**最終文書での扱い**: 観点は「1つのメソッドが1つのことをしているか」（`B-23`）にする。行数は、道具の既定値の例として1か所だけ、出典と出所（RuboCop の既定値であること）を添えて挙げる。

### D-4 「良いコード」を品質規格の用語へ写してよいか

| 者 | 立場 | 理由 | 根拠 |
|---|---|---|---|
| Claude | 見落とし | 写像は書くべきだが、規格本体を読めていない事実（`W-28`）を手引きの側にも書かないと、読者は根拠を規格までたどれない | `B-3`、`B-4`、`W-28` |
| Antigravity | 反対 | 規格本体の記述を確認できておらず二次資料の参照にとどまるため、確認が取れるまで公的規格として引用することに反対である | `B-4`、`W-28` |

**決着しない。** 2者が同じ事実（`www.iso.org` が HTTP 403 を返し、規格本体を読めていないこと）から違う結論に達した。根拠の強さで差が付かず、独立した第三の判断（codex）が無いため、どちらかに寄せる材料が無い。

**2者が一致している部分だけを採る。** 一致しているのは「規格本体を読んでいない」という事実の記載である。一致していないのは、その状態で規格の用語を使ってよいかである。

**最終文書での扱い**: 保留のときは弱いほうに合わせる。**規格の副特性の一覧（モジュール性、再利用性、解析性、修正性、試験性）を手引きの主張の根拠にしない。** 「良いコードとは保守性、とくに変更容易性が高いコードである」という趣旨は書くが、出典は `SRC-CODE-002` p.343（書籍の本文）とし、規格そのものは根拠にしない。版を書く必要が生じたときは、書籍が参照した JIS X 25010:2013 と書く。**2023年版の内容は書かない。** この判断は決着ではなく、決着しなかったときの司会の処理である。そのことを最終文書にも書く。

### D-5 テストの網羅を、どの理由で書くか

| 者 | 立場 | 理由 | 根拠 |
|---|---|---|---|
| Claude | 見落とし | 2つは結論が同じでも理由が異なり、`W-13` の NIST の実例が後者の証拠になるため、両方を書くほうが強い | `B-30`、`W-19`、`W-13` |
| Antigravity | 見落とし | 費用対効果の低さと目標値化による指標の形骸化は矛盾せず相互補完的である | `B-30`、`W-19` |

**決着**: 両方の理由を書く。`B-30`（`SRC-CODE-001` p.215-216）は費用対効果を理由にし、`W-19`（Martin Fowler）は指標のゆがみを理由にする。**別々の資料が別々の理由で同じ結論に達しており、独立している。** さらに `W-13`（NIST SP 500-235）に、指標を目標にしたときに測り方のほうがゆがんだ実例がある。

**最終文書での扱い**: 「カバレッジの数値目標を置かない」を観点として書き、理由を2つ添える。100%という数値も、90%という数値も、合否の基準としては書かない。

### D-6 「きれい」という語を使うか

| 者 | 立場 | 理由 | 根拠 |
|---|---|---|---|
| Claude | 反対 | 「見た目がきれいでも変更が大変なプログラムは多い」と一次資料が明示しているため、「きれい」を良し悪しの基準として使ってはならない | `B-9`、`B-1`、`B-3` |
| Antigravity | 反対 | 「きれい」は主観的で明確な定義が存在しない。書籍が共通して指標とする「理解までの時間」「変更容易性」に置き換えるべきである | `B-1`、`B-3`、`B-9`、`A-1`、`A-4`、`A-7` |

**決着**: 「きれい」を基準にしない。`B-9`（`SRC-DESIGN-001` p.15）が決定的である。設計文書を整備しコーディング規約に従っていても、意図が読み取りにくく変更箇所が散らばるプログラムは多い、と一次資料が明示している。**見た目の整い方と変更のしやすさは別の量である。**

置き換え先は2つで、どちらも複数の資料が独立に支持している。1つは「他の人が理解するまでの時間」（`B-1`、`SRC-CODE-001` p.24）、もう1つは「変更容易性」（`B-3`、`SRC-CODE-002` p.343）である。

**最終文書での扱い**: 章の冒頭で「この章は『きれい』を基準に使わない」と宣言し、2つの量に置き換えることを書く。整形とコーディング規約の話は、この2つの下位に置く。

### D-7 Java の悪い例・良い例で、どこまで扱うか

| 者 | 立場 | 理由 | 根拠 |
|---|---|---|---|
| Claude | 同意 | カプセル化・値オブジェクト・ファーストクラスコレクションは責務の分割の話であり章「02 設計」に属する。この章の例は1メソッド・1変数・1つの名前の水準で閉じるものに絞る | `B-38`、`B-39`、`B-45`、`B-52`、`B-53`、`B-21`、`B-55` |
| Antigravity | 見落とし | 文やメソッド単位の局所的な改善と、クラス構造に関わる設計の関心事との境界を見落としている。本章は早期 return や命名等の局所的改善に絞り、カプセル化や値オブジェクト等は次章に委ねるべきである | `B-15`、`B-17`、`B-18`、`B-20`、`B-52`、`B-53`、`A-29` から `A-35` |

**決着**: 局所的な改善に絞る。2者が同じ境界（クラス構造に関わるものを次章へ送る）を独立に提案した。

この章で扱う症状は次のとおりである。

| 症状の対 | 根拠 |
|---|---|
| 技術駆動命名・連番命名 対 目的が読み取れる名前 | `B-45`、`B-46`、`B-48` |
| 1文字名・略語 対 意味のある単語 | `B-43`、`B-49` |
| 真偽値の曖昧な名前・否定形 対 `is`／`has`／`can`／`should` の肯定形 | `B-39`、`B-40` |
| 範囲の名前の取り違え 対 `min`／`max`、`first`／`last`、`begin`／`end` | `B-38` |
| 深いネストの `if` 対 早期 return とガード節 | `B-17`、`B-52` |
| フラグ引数 対 意図ごとに分けたメソッド | `B-20`、`B-53` |
| 巨大な式 対 説明変数 | `B-21` |
| 再代入する可変の変数 対 `final` による不変 | `B-16` |
| グローバル状態・非決定的な動作 対 引数と戻り値で閉じた関数 | `B-25`、`B-26`、`B-27`、`B-55` |
| マジックナンバー 対 意図を表す定数 | `B-56`、`W-24` |

**最後の1行は、批評のあとに司会が足した。** `B-56`（`SRC-CODE-002` p.212-213）はメソッド内の数値リテラルの話であり、この論点で決まった「局所的な改善に絞る」という規則をそのまま当てはめたものである。**新しい決着ではなく、決まった規則の適用である。** 依頼で定数の命名が問われており、`W-24`（定数の表記規約）だけでは「なぜ定数にするのか」を書けないため足した。

**次章へ送る症状**: カプセル化（`B-15`）、値オブジェクト（`B-18`、`B-50`）、ファーストクラスコレクション（`A-33`）、神クラスの分割（`B-47`）。

**最終文書での扱い**: 「この章で扱わないこと」の表に、依頼で指定された5つ（パッケージ構成、共通化の判断、単一責任、YAGNI、デザインパターン）に加えて、上の4つを書く。

### D-8 命名の表記規約を、二次資料だけを根拠に書いてよいか

| 者 | 立場 | 理由 | 根拠 |
|---|---|---|---|
| Claude | 同意 | Java で悪い例と良い例を対で示す以上、表記規約なしには例が書けない。真偽値の接頭辞は書籍の一次資料が独立に支持している | `W-23` から `W-27`、`B-39` |
| Antigravity | 同意 | 書籍側でも表記規約は公開情報で補う前提とされており、広く認知された業界標準を参考規約として書くことに同意する | `W-23` から `W-26`、`A-26` |

**決着**: 書いてよい。ただし出所を明記する。`W-23` から `W-27` の出所は Google の公開する社内標準（Google Java Style Guide）であり、**規格でも標準化団体の文書でもない。** 2者が同意しているが、根拠は同じ1つの資料であるため、**この一致は2票ではない。**

強い部分と弱い部分を分ける。真偽値の接頭辞（`is`、`has`、`can`、`should`）は `B-39`（`SRC-CODE-001` p.55、一次資料）が独立に支持しており強い。大文字小文字の使い分けと頭字語の扱いは Google の1資料しか根拠が無く弱い。

**最終文書での扱い**: 表記規約は「Java の例を読むための約束」として、出所を添えて書く。手引きの原則としては書かない。**表記規約は言語ごとに違うため、原則として扱うと言語に依存する。**

### D-9 テスト容易性と設計の関係を、どちらの向きで書くか

| 者 | 立場 | 理由 | 根拠 |
|---|---|---|---|
| Claude | 見落とし | `SRC-CODE-001` は表14-1・表14-2 で「テスト容易性の問題」と「設計の問題」を並置しており、因果の向きを決める議論そのものが資料の読み違いである | `B-25`、`B-26`、`B-27`、`B-29` |
| Antigravity | 見落とし | テスト容易性と疎結合な設計は双方向で好循環を生み出す表裏一体の関係である | `B-26`、`B-28`、`B-29`、`W-18` |

**決着**: 因果の向きを決めない。同じ性質の2つの見え方として書く。

`B-26`（`SRC-CODE-001` p.214、表14-1）が根拠として強い。この表は1つの特性（例: グローバル変数を使っている）に対して「テスト容易性の問題」と「設計の問題」の2列を並べており、**著者は因果ではなく並置として書いている。** `B-29`（同 p.214）の「テストするのが難しそうと思ったら立ち止まって設計を考え直す」は、テスト容易性を設計の欠陥を見つける道具として使う、という読み方になる。

**最終文書での扱い**: 「テストしにくさは設計の欠陥を知らせる兆候である」という形で書く。「テストを書けば良い設計になる」とは書かない。テスト駆動開発の是非には触れない。`SRC-CODE-001` 自身が「よく議論になる話題なので深追いはしない」としているためである。
