## この調査の位置づけ

`docs/index.md` の章の一覧にある「05 テスト」を書くための調査である。**新しい文書は作らない。**

主に使う出典は `SRC-TEST-001`（ソフトウェアテスト徹底指南書）、`SRC-TEST-002`（現場の仕事がバリバリ進む ソフトウェアテスト手法）、`SRC-CODE-001`（リーダブルコード）14章である。抽出テキストは `research/extracted/` にある。**再抽出は不要である。**

## 先に書いた章との関係

**章「01 良いコードとは何か」（接頭辞 `GC-`、観点17件）、章「02 設計」（`DS-`、16件）、章「03 アーキテクチャ」（`AR-`、18件）、章「04 コードレビュー」（`RV-`、25件）が公開ずみである。** この章の接頭辞は `TS-` とする。

**テストしやすいコードの性質は章01 が持っている。** `GC-10`（グローバル状態）、`GC-11`（非決定的な動作）、`GC-12`（テストしにくさを設計の兆候として読む）、`GC-13`（カバレッジの数値目標を置かない）である。**この章はそれを作り直さず、テストの側の観点だけを書く。**

| 章 | 持っているもの | この章での扱い |
|---|---|---|
| 章01（`GC-`） | テストしやすいコードの性質、カバレッジを目標にしない立場 | 既存の観点IDを指して済ませる |
| 章02（`DS-`） | 責務の分割、依存の向き | テストの単位を決めるときに指す |
| 章03（`AR-`） | 層の分担、品質特性 | テストの層を決めるときに指す |
| 章04（`RV-`） | レビューの場での見方 | テストの有無をレビューで見る点で接する |
| この章（`TS-`） | 観点の出し方、設計技法、自動化の判断、停止の条件 | 本文で書く |

**`GC-13` は「カバレッジの数値目標を置かない」を既に言い切っている。** この章はそれを繰り返さず、「では何で停止を決めるのか」を書く。

## 中心の問い

**中心の問いは2つである。「テストの抜けをどうやって減らすのか」と「どこで止めてよいと言えるのか」である。** 以下の問いは、この2問を答えられる大きさに割ったものである。

## 答える問い

| 問い | 内容 | 主に答える系統 |
|---|---|---|
| `Q1` | テストの観点をどうやって出すのか。何を手がかりにして抜けを減らすのか。仕様書だけを見て出すのか、他に手がかりはあるか。観点を整理する枠組み（テスト分析、テスト条件、品質特性、ソフトウェア品質モデル）はあるか | 書籍 |
| `Q2` | テストケースをどう設計するのか。同値分割、境界値分析、デシジョンテーブル、状態遷移、組み合わせの技法を、いつどの場面で使い分けるのか。技法ごとに前提と限界は何か | 書籍 |
| `Q3` | 何を自動化し、何を自動化しないのか。判断の基準は何か。テストの層（単体・結合・エンドツーエンド）をどう分け、どの層にどれだけ置くのか。自動化の費用と保守の負担をどう見積もるのか | 公開情報 |
| `Q4` | どこまでテストしたら十分と言えるのか。停止の条件をどう決めるのか。カバレッジの数値目標以外に、どんな停止の基準があるのか。リスクや欠陥の検出曲線を使う方法はあるか | 公開情報 |
| `Q5` | 良いテストコードと悪いテストコードの違いは何か。テストの読みやすさ、壊れにくさ、失敗したときの分かりやすさを、何で判断するのか。テストが本体コードの変更で壊れるのは、いつ問題でいつ問題でないのか | 書籍 |

**問いは4系統すべてに同じものを渡す。** 「主に答える系統」は重み付けであり、担当の分割ではない。

**依頼元が最も迷っているのは `Q1` と `Q4` である。** 調査の重みをこの2つに置く。

## 例示に使う言語

**この章は2種類の例を、悪い例と良い例の対で示す。**

| 例の種類 | 書き方 |
|---|---|
| テストコード | ` ```java ` のブロック。素の Java で10行から25行。JUnit などのフレームワークに依存しない |
| テストケースの一覧 | 表または ` ```text ` のブロック |

**どちらも、そのあとに「なぜ悪いのか」「なぜ良いのか」を文章で説明する。** 並べるだけにしない。実在の製品名やフレームワークに依存しない素の Java で書く。アサーションは素朴なメソッドとして書いてよい。
