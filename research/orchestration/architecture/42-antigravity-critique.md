| `D-1` | 見落とし | 「画面が1つだけ」と「サーバ側の集約量」は二者択一ではなく、単一画面であっても大量の集約が必要な場合はBFFが有効となるため双方の条件を連動して見る必要がある。 | `W-15`, `B-24`, `A-12` |
| `D-2` | 同意 | UX向上のための形式的な入力検証は両側に重複して置いてよいが、ビジネスの不変条件を守る判定や計算ロジックはAPI側にのみ置くべきである。 | `W-34`, `W-35`, `A-21`, `A-22` |
| `D-3` | 同意 | サービス間の結合度を高める共有ライブラリの抽出は避け、BFF間の重複を許容するか業務領域を表す新サービスとして切り出すべきである。 | `B-38`, `B-39`, `B-40`, `A-17` |
| `D-4` | 見落とし | GraphQLを単なるBFFの代替と捉えるのは不十分であり、クライアント起点の動的な集約と絞り込みを実現するBFFの有力な実装技術である点を見落としている。 | `W-29`, `B-82`, `A-18` |
| `D-5` | 見落とし | 構造の最上位を二者択一で捉えるのではなく、システムの規模拡大に伴い最上位を業務領域で分割したうえでその内部を層に分けるという進化の視点を見落としている。 | `W-46`, `W-47` |
| `D-6` | 見落とし | スループット向上の観点から専任チームを排してストリームアラインドチームとすべきとされる一方、専門家不足や一貫性の課題を解消する具体的手段が資料から抜け落ちている。 | `B-42`, `B-43`, `B-44`, `A-29` |
| `D-7` | 同意 | 利用者体験やクライアントの特性を反映しつつも、組織の自律性を高めるためコンウェイの法則に従ってチーム境界に合わせてBFFの数を決定すべきである。 | `W-19`, `B-33`, `A-9`, `A-28` |
| `D-8` | 同意 | 提供側に利用側の知識が侵入して結合度が高まるのを防ぐため、複数サービスをまたぐ複合的な集約はAPIを利用する側が開発すべきである。 | `B-12`, `B-13`, `A-8` |
| `D-9` | 同意 | 交渉不可能な制約を最優先にする指針はあるものの、品質特性・変更頻度・チーム分割の間で普遍的な優先順位を定めた資料は存在しない。 | `B-66`, `A-26` |
| `D-10` | 反対 | 提唱者自身が「経験則のような気がする」と留保を付けた格言に過ぎず、サービス水準を決定する客観的・決定的な判断基準としては不十分である。 | `B-41` |
| `D-11` | 見落とし | コンウェイの法則に基づく定性的なプラクティスとしては支持されているものの、その有効性や成功確率を実証的に示した客観的データが資料から見落とされている。 | `W-42`, `W-45`, `A-30` |
| `D-12` | 同意 | BFFの運用負担やトレードオフに関する定性的な記述はあるものの、保守費用を実測・比較した定量的な資料は存在しない。 | `W-26`, `B-28`, `A-26` |
