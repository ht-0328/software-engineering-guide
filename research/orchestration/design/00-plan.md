## この調査の位置づけ

`docs/index.md` の章の一覧にある「02 設計」を書くための調査である。**新しい文書は作らない。**

主に使う出典は `SRC-DESIGN-001`（現場で役立つシステム設計の原則）、`SRC-DESIGN-002`（Head First デザインパターン 第2版）、`SRC-CODE-002`（改訂新版 良いコード／悪いコードで学ぶ設計入門）、`SRC-THINK-001`（システム開発と「具体と抽象」）である。抽出テキストは `research/extracted/` にある。**再抽出は不要である。**

## 先に書いた章との関係

**章「01 良いコードとは何か」（`docs/01-good-code.md`）が公開ずみである。観点IDの接頭辞は `GC-` である。** この章の接頭辞は `DS-` とする。

**章01 と重複する観点は書かない。** 章01 は「1つのメソッドが1つのことをしているか」（`GC-04`）をメソッドの水準で扱った。この章の「単一責任」は、クラスと責務の水準で書く。命名の一般則（`GC-14` から `GC-17`）も章01 が持つ。この章が扱うのは、クラスとパッケージの名前だけである。

## 答える問い

| 問い | 内容 | 主に答える系統 |
|---|---|---|
| `Q1` | 単一責任の「単一」とは、何をもって単一と言うのか。「1つのことをする」の1つを、どう数えるのか。クラスの責務を切る単位は何か | 書籍 |
| `Q2` | 共通化するかどうかの判断基準は何か。同じに見えるコードを、まとめてよいときと、まとめてはいけないときの見分け方は何か | 書籍 |
| `Q3` | パッケージ構成をどう考えるか。何を単位に分けるのか。層で分けるのか、業務の領域で分けるのか | 書籍 |
| `Q4` | `Util`、`Common`、`Manager`、`Helper` のような名前を付けたくなるとき、なぜその名前が問題なのか。代わりに何と名付けるのか | 書籍 |
| `Q5` | 変更容易性と YAGNI がぶつかったとき、どちらを優先するのか。「将来の変更に備えた抽象化」と「今必要ないものは作らない」の線引きはどこか | 公開情報 |
| `Q6` | デザインパターンは、どういうときに使うと便利なのか。代表的なパターンを3つから5つ選ぶとき、それぞれ「どんな問題が起きているときに効くか」は何か | 書籍 |

**問いは4系統すべてに同じものを渡す。** 「主に答える系統」は重み付けであり、担当の分割ではない。

**依頼元が最も迷っているのは `Q1`、`Q2`、`Q4`、`Q5` である。** 調査の重みをこの4つに置く。

## 例示に使う言語

**サンプルコードは Java で書き、悪い例と良い例を対で示す。** ただし Java は例示のための言語であり、原則そのものは言語に依らない。実在の製品名やフレームワークに依存しない素の Java で書く。

コードは10行から25行程度にする。**パッケージ構成の説明だけは、コードではなくディレクトリ木で悪い例と良い例を示す。**

### codex の失敗が結論に与える影響

**codex は4系統のうち、書籍と公開情報の両方を独立に確かめる役だった。** 今回は次のようになった。

| 面 | 独立に調べた者の数 |
|---|---|
| 書籍（4冊） | 2（司会と Antigravity） |
| 公開情報 | 1.5（司会が12件、Antigravity は Fowler「Yagni」1件のみ） |

**公開情報の側は、実質的に司会の1系統である。** `10-web.md` の主張のうち、`W-29`（JDK の `java.util.Objects`）、`W-17` から `W-23`（Martin「Granularity」）、`W-58`（Kohavi ほか）は、他者の検証を受けていない。
