## この調査の位置づけ

`docs/index.md` の章の一覧にある「07 仕事の進め方」を書くための調査である。**新しい文書は作らない。**

主に使う出典は `SRC-THINK-001`（システム開発と「具体と抽象」）、`SRC-REVIEW-001`（コードレビューの教科書）、`SRC-ARCH-001`（Design It!）である。`SRC-ARCH-002`（マイクロサービスアーキテクチャ 第2版）にもチームと仕事の分け方の記述がある。抽出テキストは `research/extracted/` にある。**再抽出は不要である。**

**書籍の根拠が薄くなりやすい題材である。** 手元の22冊は、見積りと合意を主題として扱っていない。**公開情報の調査を厚くする。根拠が足りない問いは、足りないと書く。**

## 中心の問い

**中心の問いは2つである。「どこまで決まれば着手してよいと言えるのか」と「何を残せば、あとで読まれる記録になるのか」である。** 以下の問いは、この2問を答えられる大きさに割ったものである。

## 答える問い

| 問い | 内容 | 主に答える系統 |
|---|---|---|
| `Q1` | 仕事をどう分割するのか。1つの単位をどこで切るのか（機能、層、工程、価値、変更の単位）。切りすぎ・切らなすぎの害は何か。分割の大きさに目安の数値はあるか。分割が正しいかを着手前に確かめる方法はあるか | 公開情報 |
| `Q2` | 見積りをどう出すのか。手法（相対見積り、三点見積り、実績からの外挿、参照クラス予測）に根拠のある比較はあるか。見積りが外れたときにどう扱うのか。**見積りを約束として扱ってよいのか。** 見積りと約束（コミットメント）を分ける根拠はあるか | 公開情報 |
| `Q3` | 着手前の合意をどう取るのか。何が決まれば着手してよいと言えるのか。受け入れ条件、完了の定義、着手の条件に、資料の裏づけはあるか。合意を取る相手は誰か。合意が取れていない状態で着手した場合、何が起きるのか | 公開情報 |
| `Q4` | 何を記録に残すのか。**残す価値のある記録と、残しても読まれない記録の違いは何か。** 記録の種類（決定記録、課題、コミットメッセージ、変更履歴、事後の振り返り）ごとに、残す項目と残さない項目に資料の裏づけはあるか。記録が陳腐化したときにどう扱うのか | 公開情報 |
| `Q5` | 進め方が失敗するときの型は何か。分割せずに着手する、見積りを約束に変える、口頭で合意して残さない、記録を書くが読まれない、といった型に名前と根拠はあるか。**悪い例と良い例を対で示せる材料**（課題や作業単位の書き方、決定記録の書き方、コミットメッセージの書き方、変更履歴の書き方）は何か | 書籍 |

**問いは4系統すべてに同じものを渡す。** 「主に答える系統」は重み付けであり、担当の分割ではない。

**依頼元が最も迷っているのは `Q2` と `Q4` である。** 調査の重みをこの2つに置く。

## 例示に使う言語

**この章は2種類の例を、悪い例と良い例の対で示す。**

| 例の種類 | 書き方 |
|---|---|
| 課題や作業単位の書き方 | ` ```text ` のブロックまたは表 |
| 記録（決定記録、コミットメッセージ、変更履歴）の書き方 | ` ```text ` のブロック |
| Java のコード | ` ```java ` のブロック。素の Java で10行から25行 |

**Java のコードは、題材に合う観点があるときにだけ付ける。** 無理に付けない。**この章はコードそのものより進め方を扱う。** 合わない観点は、表と手順の一覧で示す。

**どの例も、そのあとに「なぜ悪いのか」「なぜ良いのか」を文章で説明する。** 並べるだけにしない。

## このリポジトリ自身を実例に使う

**このリポジトリは決定記録（`docs/adr/`）を持っている。** 記録の残し方を書くとき、実例として参照してよい。**ただし決定記録は公開サイトに出していない。** 章から `docs/adr/` へリンクすると、サイト生成のときに GitHub の URL へ差し替わる。それでよい。
