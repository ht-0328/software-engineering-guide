## この手引きは何か

**開発の現場で繰り返し必要になる判断を、根拠つきの観点に変えるための手引きである。**

扱うのは次の7つである。

- 良いコードの基準
- 設計とアーキテクチャの考え方
- コードレビューの観点
- テストの観点
- 問題の見つけ方
- 仕事の進め方
- 画面とインターフェースの設計

**書くのは「考え方」であって、特定の言語や製品の使い方ではない。** 技術の細部は寿命が短く、手引きの形で保守するのに向かないためである。

## 何が根拠になっているか

**手元の書籍22冊を一次資料とする。** 一覧と出典IDは [出典カタログ](../research/sources.md) にある。

書籍で足りない範囲は、公開されている規格と各社の公開標準で補う。**URLと確認日を記録し、`research/external/` に置く。**

この手引きは、次の3つの規則で書く。

1. **主張には出典IDと該当箇所を添える。** 出典が無い記述は「出典なし・私見」と明記する。
2. **1冊にしか根拠が無いものは、そう分かるように書く。** 複数の本が支持する原則と区別できて初めて、読者は重みを判断できる。
3. **数値は目安として書く。** 「1関数30行以内」のような数値は、出典の文脈から離れると合否の基準に見えてしまう。

## 文書の書き方の規則

**この手引き自身の書き方は、姉妹リポジトリ [エンジニアのためのドキュメント標準](https://ht-0328.github.io/engineering-docs-standard/) に従う。** 同じ規則を2か所に書くと、直したそばから食い違うためである。

機械で検査できる範囲は `.doclint.yml` に書いてあり、[tools/doc_lint.py](../tools/doc_lint.py) で検査する。手順は [README](../README.md) にある。

## 章の書き方

**節の並びは8章で共通にする。節の中の書き方は、観点ごとに必要なものだけを置く。** 読者が章をまたいで探せるようにしつつ、同じ形を機械的に並べないためである。書式は [templates/chapter.md](../templates/chapter.md) にある。

| 節 | 内容 |
|---|---|
| 導入（h1 の直後） | その章が要る場面を具体で1段落 |
| この章で判断できること | 想定読者、答える問い、読んだあとにできること |
| 結論 | 章の主張。地の文で書き、件数は固定しない |
| 主題ごとの節 | 節の頭に導入を置く。中に観点を並べる |
| この章で扱わないこと | 範囲の外にあるものと、その理由 |
| 決着していないこと | 調査で決着しなかったもの |
| 観点の一覧 | 引くための索引。**末尾に置く** |
| 出典 | 出典IDと書名の対応、使った箇所、支持する観点 |
| 文書情報 | 作成者、機密区分、保守責任者、最終確認日 |

観点IDは章ごとに接頭辞を変える。**本文中の観点を、レビューの指摘やチェックリストから一意に指せるようにするためである。**

### 観点の書き方

**観点は地の文で書く。** 「何を見るか」「なぜそう言えるか」「判断に迷う例」のような太字のラベルを全観点に並べない。同じ形が続くと走査の手がかりにならず、迷う例が無い観点にも無理に書くことになる。

| 決めごと | 内容 |
|---|---|
| 見出し | 観点IDと、観点を文で書いたものにする |
| 本文 | 1段落1アイデア。段落の最初の文に結論を置く |
| 書名 | 地の文で名乗らせる。**出典IDを本文に書かない** |
| 根拠 | 観点の末尾に `**根拠**:` の1行を置き、出典IDとページをまとめる |
| 例・表・図 | **必要な観点にだけ**置く。全観点に同じ形を並べない |
| 専門用語 | 初出の語に、その場で短い言い換えを添える |

**この書き方は、姉妹リポジトリの標準に合わせたものである。** 決めた経緯は `research/orchestration/readability/40-debate.md` にある。
