## この手引きは何か

**開発の現場で繰り返し必要になる判断を、根拠つきの観点に変えるための手引きである。**

扱うのは次の6つである。

- 良いコードの基準
- 設計の考え方
- コードレビューの観点
- テストの観点
- 問題の見つけ方
- 仕事の進め方

**書くのは「考え方」であって、特定の言語や製品の使い方ではない。** 技術の細部は寿命が短く、手引きの形で保守するのに向かないためである。

## 何が根拠になっているか

**手元の書籍22冊を一次資料とする。** 一覧と出典IDは [出典カタログ](../research/sources.md) にある。

書籍で足りない範囲は、公開されている規格と各社の公開標準で補う。**URLと確認日を記録し、`research/external/` に置く。**

この手引きは、次の3つの規則で書く。

1. **主張には出典IDと該当箇所を添える。** 出典が無い記述は「出典なし・私見」と明記する。
2. **1冊にしか根拠が無いものは、そう分かるように書く。** 複数の本が支持する原則と区別できて初めて、読者は重みを判断できる。
3. **数値は目安として書く。** 「1関数30行以内」のような数値は、出典の文脈から離れると合否の基準に見えてしまう。

## 文書の書き方の規則

**この手引き自身の書き方は、姉妹リポジトリ [エンジニアのためのドキュメント標準](https://ht-0328.github.io/engineering-docs-standard/) に従う。** 同じ規則を2か所に書くと、直したそばから食い違うためである。

機械で検査できる範囲は `.doclint.yml` に書いてあり、[tools/doc_lint.py](../tools/doc_lint.py) で検査する。手順は [README](../README.md) にある。

## 章の書き方

**すべての章は同じ形をとる。** 読者が章をまたいで探せるようにするためである。

| 節 | 内容 |
|---|---|
| 3行で | その章の結論。急ぐ読者はここだけ読む |
| 観点の一覧 | 1行が1観点の表。観点IDを振る |
| 各観点 | 何を見るか、なぜそう言えるか（出典ID）、判断に迷う例 |
| この章で扱わないこと | 範囲の外にあるものと、その理由 |
| 出典 | この章が使った出典IDと該当箇所 |

観点IDは章ごとに接頭辞を変える。**本文中の観点を、レビューの指摘やチェックリストから一意に指せるようにするためである。**
