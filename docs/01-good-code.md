## 3行で

1. **「きれい」を基準にしない。** 見た目が整っていても変更が大変なプログラムは多い（`SRC-DESIGN-001` p.15）。この章は「他の人が理解するまでの時間」と「変更容易性」の2つに置き換える。
2. **テストしにくさは、設計の欠陥を知らせる兆候である。** グローバル状態・多すぎる依存・非決定的な動作は、テストの問題であると同時に設計の問題である（`SRC-CODE-001` p.214）。
3. **名前の長さは、その名前が見える範囲で決める。** 数行しか見えない変数は短くてよく、フィールドと公開メソッドは完全な単語にする（`SRC-CODE-001` p.44、`SRC-DESIGN-001` p.17-18）。

## 「きれい」を基準にしない理由

**この章は「きれい」「美しい」を良し悪しの基準として使わない。** 理由は、一次資料が両者を切り離しているためである。

`SRC-DESIGN-001` p.15 は、設計文書を整備しコーディング規約に従っていても変更が大変なプログラムは多い、と述べる。見た目がきれいでも、意図が読み取りにくく、変更箇所があちこちに散らばるコードがある。**整形の状態と、変更のしやすさは別の量である。**

代わりに使う量は2つである。どちらも複数の資料が独立に支持している。

| 量 | 定義 | 出典 |
|---|---|---|
| 理解までの時間 | 他の人がそのコードを読んで理解するまでにかかる時間 | `SRC-CODE-001` p.24（1.2） |
| 変更容易性 | なるべくバグを出さずに、どれだけ速く正確にコードを変更できるか | `SRC-CODE-002` p.343（16.1） |

**この2つは直接には測れない。** 変更容易性は未来の変更コストの低さを示すものであり、経時変化で表出する（`SRC-CODE-002` p.351-352）。測れないからこそ、観点の形にして目で確かめる。

## 判断の基準

**良し悪しをどこで決めるかを、3つの観点で書く。**

### GC-01 他の人が理解するまでの時間で判断しているか

**何を見るか**: 自分が読めるかではなく、そのコードを初めて読む人が理解するまでにどれだけかかるかで判断しているか。

**なぜそう言えるか**: `SRC-CODE-001` p.23-24（1.1、1.2）は「コードは他の人が最短時間で理解できるように書かなければいけない」を鍵となる考えとして置く。同書 p.24 は、同僚に読んでもらって理解までの時間を計るという測り方まで示している。

**判断に迷う例**: 行数を減らすと理解が速くなるとは限らない。`SRC-CODE-001` p.25、p.110 は、行数を短くするよりも理解にかかる時間を短くするほうが大切だと述べる。**行数の削減が理解を妨げるなら、行数を増やす選択が正しい。**

### GC-02 整形の状態と変更容易性を分けて見ているか

**何を見るか**: 「規約に従っている」「整形されている」を、変更しやすさの証拠として使っていないか。

**なぜそう言えるか**: `SRC-DESIGN-001` p.15 は、設計文書を整備しコーディング規約に従っていても変更が大変なプログラムは多い、と述べる。同書 p.16 は、小さな修正のたびにメソッドが数行伸び、クラスが膨らみ、引数が増えていく負の循環を挙げる。**変更が変更を難しくする。**

**判断に迷う例**: 整形の指摘そのものは無駄ではない。ただし、整形を直しても変更容易性は上がらない。`SRC-CODE-002` p.343-344 は、変更容易性が低いと開発生産性が落ちる要因を2つ挙げる。関係するロジックが散在して修正漏れが起きること、可読性が下がって関連ロジックを探し回る手間が増えることである。

### GC-03 指標を目標値にしていないか

**何を見るか**: 循環的複雑度やカバレッジのような指標を、達成すべき目標値として運用していないか。

**なぜそう言えるか**: `SRC-EXT-001`（NIST SP 500-235）§2.5 は、複雑度の上限をいくつにするかは決着していない（controversial）と自ら述べる。同文書が最も有効とする方針は「各モジュールの複雑度を10に抑えるか、超えた理由を文書で示すかのどちらかにする」である。同 §2.5 には、複雑度90のモジュールに何もしない10分岐を足して「修正複雑度10」に見せた実例が載っている。**測り方をゆがめれば数値は達成できる。**

`SRC-EXT-003`（Martin Fowler「TestCoverage」）も、カバレッジを目標値にすると質の低いテストで数値だけを満たせると述べる。

**判断に迷う例**: 10という数値は目安として使ってよい。合否の基準としては使わない。**この手引きは、循環的複雑度に対応するバグ混入確率の数値を書かない。** `SRC-CODE-002` p.354 の表にはその数値がある。ただし同書は脚注で、MathWorks 社の目安を引用したものだと断っている。**測定条件が示されていない。**

## 変更しやすいコードの性質

**変更が大変なプログラムの特徴は3つである。メソッドが長い、クラスが大きい、引数が多い**（`SRC-DESIGN-001` p.15）。この3つは互いを悪化させる。引数が多ければメソッドが長くなり `if` 文が増え、長いメソッドが増えればクラスが肥大化する。

### GC-04 1つのメソッドが1つのことをしているか

**何を見るか**: メソッドが複数の関心事を抱えていないか。名前が「〜と〜」でしか説明できないメソッドになっていないか。

**なぜそう言えるか**: `SRC-CODE-001` p.165（11章）は「コードは1つずつタスクを行うようにしなければいけない」を鍵となる考えとする。`SRC-DESIGN-001` p.15 は、大きなクラスと多い引数に共通する問題を「関心事の詰め込みすぎ」と呼ぶ。変更のときに、どの部分が関係するかの見極めに時間がかかる。

**判断に迷う例**: 行数を上限として運用しない。`SRC-CODE-002` p.353 は、コード行数の上限の例として Ruby の解析ライブラリ RuboCop の既定値（メソッド10行以内、クラス100行以内）を挙げる。**この数値の裏づけは著者の現場経験であり、測定ではない**（同書 脚注7）。目安として持ち、合否には使わない。

### GC-05 引数が多すぎないか。フラグ引数が無いか

**何を見るか**: メソッドの動きを切り替える `boolean` 型の引数（フラグ引数）が無いか。

**なぜそう言えるか**: `SRC-CODE-002` p.192（8.6）は、フラグ引数付きのメソッドが何が起こるかを読み手に想像させると述べる。理解するには、メソッド内部を見に行くしかない。同書 p.269（13.5.2）は「フラグ引数は使わない」を明示の指針として置く。

**悪い例**

```java
public void applyDamage(boolean isMagic, int amount) {
    if (isMagic) {
        magicPoint = Math.max(0, magicPoint - amount);
    } else {
        hitPoint = Math.max(0, hitPoint - amount);
    }
}

// 呼び出し側
applyDamage(true, 30);
applyDamage(false, 12);
```

**良い例**

```java
public void applyMagicDamage(int amount) {
    magicPoint = Math.max(0, magicPoint - amount);
}

public void applyPhysicalDamage(int amount) {
    hitPoint = Math.max(0, hitPoint - amount);
}

// 呼び出し側
applyMagicDamage(30);
applyPhysicalDamage(12);
```

**なぜ悪いのか**: 呼び出し側の `applyDamage(true, 30)` を読んでも、`true` が何を意味するかが分からない。読み手は `applyDamage` の中を開いて `isMagic` の分岐をたどる必要がある。引数の並びを間違えても、コンパイルは通る。

**なぜ良いのか**: メソッド名が処理の内容そのものになり、呼び出し側だけで意味が閉じる。分岐が消えるため、それぞれのメソッドは1つのことしかしなくなる（`GC-04`）。

**判断に迷う例**: 引数の数そのものに上限は置かない。`SRC-DESIGN-001` p.15 は引数の多さを特徴として挙げるが、数値は示していない。**この手引きも数値を置かない。**

### GC-06 分岐が深くなっていないか

**何を見るか**: `if` のネストが深くなっていないか。処理の対象外を先頭で除外できないか。

**なぜそう言えるか**: `SRC-CODE-002` p.48（3章）は、処理の対象外となる条件を先頭に定義する方法をガード節と呼ぶ。不要な要素を先頭で除外すると、後続のロジックが単純になる。同書 p.149（8.1）は、早期 return によるネストの解消を示す。

**悪い例**

```java
public int calculateShippingFee(Order order) {
    if (order != null) {
        if (order.hasItems()) {
            if (order.isDomestic()) {
                if (order.totalPrice() >= 3000) {
                    return 0;
                } else {
                    return 500;
                }
            } else {
                return 2000;
            }
        } else {
            return 0;
        }
    } else {
        return 0;
    }
}
```

**良い例**

```java
public int calculateShippingFee(Order order) {
    if (order == null) {
        return 0;
    }
    if (!order.hasItems()) {
        return 0;
    }
    if (!order.isDomestic()) {
        return 2000;
    }
    if (order.totalPrice() >= 3000) {
        return 0;
    }
    return 500;
}
```

**なぜ悪いのか**: 最後の `return 500` にたどり着く条件を知るには、4段の `if` と4つの `else` を頭の中で組み合わせる必要がある。条件を1つ足すたびにネストが1段深くなり、既存の `else` の対応関係も読み直すことになる。

**なぜ良いのか**: 1行の `return` が1つの条件に対応する。上から順に読むだけで、除外される場合が分かる。条件を足すときは `return` を1つ足すだけで済み、既存の行を読み直す必要が無い。

**判断に迷う例**: 早期 `return` が10個並ぶなら、そのメソッドが多くのことを抱えている（`GC-04`）。ネストの解消はメソッドの分割を不要にするものではない。

### GC-07 巨大な式に名前が付いているか

**何を見るか**: 条件式や計算式が長くなったとき、途中に名前を置いているか。

**なぜそう言えるか**: `SRC-CODE-001` p.121（8.1）は、式を表す変数を「説明変数」と呼び、式の意味を変数名が説明してくれると述べる。同書 p.121（8章）は「巨大な式は飲み込みやすい大きさに分割する」を鍵となる考えとする。

**悪い例**

```java
public boolean canPlaceOrder(Customer customer, Cart cart) {
    return customer.getStatus() == Status.ACTIVE
        && !customer.isSuspended()
        && cart.getItems().size() > 0
        && cart.getTotalPrice() >= 500
        && cart.getTotalPrice() <= 1000000;
}
```

**良い例**

```java
public boolean canPlaceOrder(Customer customer, Cart cart) {
    boolean isValidCustomer =
        customer.getStatus() == Status.ACTIVE && !customer.isSuspended();
    boolean hasItems = cart.getItems().size() > 0;
    boolean isWithinPriceRange =
        cart.getTotalPrice() >= 500 && cart.getTotalPrice() <= 1000000;

    return isValidCustomer && hasItems && isWithinPriceRange;
}
```

**なぜ悪いのか**: 5つの条件が同じ高さで並んでおり、どれが顧客の話でどれが買い物かごの話かを読み手が仕分ける必要がある。条件が失敗したときに、どのまとまりが原因かをデバッガで追うこともできない。

**なぜ良いのか**: 3つの名前が、条件のまとまりを説明する。最後の `return` を読むだけで注文できる条件の骨格が分かる。デバッグのときも、どの変数が `false` かを見れば原因が絞れる。

**判断に迷う例**: 説明変数を置くと行数は増える。行数の増加は問題ではない。`SRC-CODE-001` p.110 は、行数を短くするより理解にかかる時間を短くするほうが大切だと述べる。

### GC-08 変数の見える範囲が狭く、再代入が無いか

**何を見るか**: 変数が見えるコードの行数が広がっていないか。生成後に値が書き換わっていないか。

**なぜそう言えるか**: `SRC-CODE-001` p.136（9.2）は「変数のことが見えるコード行数をできるだけ減らす」を鍵となる考えとする。同書 p.145 は「変数を操作する場所が増えると、現在値の判断が難しくなる」と述べる。

`SRC-CODE-002` p.55、p.57（4章）は、次の3つを同時に行うことを勧める。コンストラクタで値を確定する。ガード節で不正値を弾く。`final` で不変にする。こうすると、未初期化のオブジェクト・不正値の混入・思わぬ副作用の3つが同時に消える。

**悪い例**

```java
public class Money {
    int amount;
    String currency;

    public Money() {
    }

    public void setAmount(int amount) {
        this.amount = amount;
    }

    public void add(Money other) {
        this.amount += other.amount;
    }
}
```

**良い例**

```java
public class Money {
    private final int amount;
    private final String currency;

    public Money(int amount, String currency) {
        if (amount < 0) {
            throw new IllegalArgumentException("金額は0以上である");
        }
        if (currency == null) {
            throw new IllegalArgumentException("通貨は必須である");
        }
        this.amount = amount;
        this.currency = currency;
    }

    public Money add(Money other) {
        return new Money(this.amount + other.amount, this.currency);
    }
}
```

**なぜ悪いのか**: `new Money()` で作った時点では金額も通貨も決まっておらず、`setAmount` を呼び忘れたインスタンスが動き回る。`add` が自分の状態を書き換えるため、同じ `Money` を参照している別の場所の値も変わる。バグが出たときに、どこで値が変わったかを追跡する範囲がクラス全体に広がる。

**なぜ良いのか**: コンストラクタを通らずにインスタンスは作れず、不正値はその場で弾かれる。`final` により、生成後の値は変わらない。`add` が新しいインスタンスを返すため、呼び出し元の `Money` は影響を受けない。**値がどこで変わったかを探す作業が消える。**

**判断に迷う例**: すべてを不変にできるとは限らない。不変にできない場合は、値を書き換える場所を1か所に集める。`SRC-CODE-001` p.145 の「操作する場所が増えると現在値の判断が難しくなる」が、そのまま判断の基準になる。

### GC-09 関係するロジックが散在していないか

**何を見るか**: 1つの仕様を変えるときに、直す場所が複数のファイルに散らばっていないか。

**なぜそう言えるか**: `SRC-CODE-002` p.343-344（16.2.1、16.2.2）は、変更容易性が低いことによる生産性の低下の要因を2つ挙げる。1つは、関係し合うロジックが散在して修正漏れが起きることである。もう1つは、関連するロジックを探し回る手間が増えることである。

**判断に迷う例**: 散在の解消は、責務の分割の設計に踏み込む。**この章では「散らばっているか」を観点として見るところまでにとどめる。** どう分けるかは章「02 設計」が扱う。

## テストしやすいコードの性質

**テストしやすいコードには3つの性質がある。明確なインタフェースがある。状態や「セットアップ」が無い。検査するデータが隠されていない**（`SRC-CODE-001` p.214）。

`SRC-CODE-001` p.214-215 は、テスト容易性の低い特性と高い特性を2つの表で並べる。**表はどちらも「テスト容易性の問題」と「設計の問題」を並置しており、著者は因果の向きを決めていない。** この章もどちらが原因かは書かない。

### GC-10 グローバル状態に依存していないか

**何を見るか**: 静的な可変フィールドや、シングルトンの可変状態に依存していないか。

**なぜそう言えるか**: `SRC-CODE-001` p.214（表14-1）は、グローバル変数を使っているコードに2つの問題を挙げる。テスト側の問題は「グローバルの状態をテストごとに初期化する必要がある」ことである。設計側の問題は「どの関数にどんな副作用があるのかわかりにくい」ことである。

**悪い例**

```java
public class TaxCalculator {
    public static double rate = 0.10;

    public static int applyTax(int price) {
        return (int) (price * (1 + rate));
    }
}

// テストにあたるコード
void reducedTaxRate() {
    TaxCalculator.rate = 0.08;   // 他のテストへ漏れる
    assert TaxCalculator.applyTax(100) == 108;
}
```

**良い例**

```java
public class TaxCalculator {
    private final double rate;

    public TaxCalculator(double rate) {
        this.rate = rate;
    }

    public int applyTax(int price) {
        return (int) (price * (1 + this.rate));
    }
}

// テストにあたるコード
void reducedTaxRate() {
    TaxCalculator calculator = new TaxCalculator(0.08);
    assert calculator.applyTax(100) == 108;
}
```

**なぜ悪いのか**: `rate` を書き換えたテストが、次に走るテストへ影響する。テストの成否が実行順に左右され、単独で走らせたときと全体で走らせたときで結果が変わる。本番コードの側でも、誰が `rate` を書き換えたかを追う手段が無い。

**なぜ良いのか**: 税率がインスタンスごとに閉じるため、テストは互いに干渉しない。税率が引数として外から見えるため、どの値で計算しているかがコードを読むだけで分かる。

**判断に迷う例**: 定数（`static final` で深く不変なもの）はグローバル状態ではない。`SRC-EXT-004`（Google Java Style Guide §5.2.4）は、定数を「深く不変で、観測できる副作用を持たない `static final` フィールド」に限っている。**書き換わらないものは、テストごとの初期化を必要としない。**

### GC-11 非決定的な動作を直接持っていないか

**何を見るか**: 現在時刻、乱数、外部との通信を、ロジックの中で直接取得していないか。

**なぜそう言えるか**: `SRC-CODE-001` p.214（表14-1）は、非決定的な動作をするコードに2つの問題を挙げる。テスト側の問題は「テストは当てにならず、信頼できない」ことである。設計側の問題は「再現不可能なバグが発生する」ことである。

`SRC-EXT-005`（Martin Fowler「UnitTest」）も同じ向きの主張をする。テストダブルは、外部サービスとの通信の非決定性を取り除くのに有効である。

**悪い例**

```java
public class Coupon {
    private final LocalDate expiresOn;

    public Coupon(LocalDate expiresOn) {
        this.expiresOn = expiresOn;
    }

    public boolean isExpired() {
        return LocalDate.now().isAfter(expiresOn);
    }
}
```

**良い例**

```java
public class Coupon {
    private final LocalDate expiresOn;

    public Coupon(LocalDate expiresOn) {
        this.expiresOn = expiresOn;
    }

    public boolean isExpiredOn(LocalDate today) {
        return today.isAfter(expiresOn);
    }
}
```

**なぜ悪いのか**: `isExpired` の結果が実行した日に依存する。有効期限の境界をテストするには、システム時刻を操作するか、実行日を待つしかない。テストが日付をまたいで壊れることもある。

**なぜ良いのか**: 判定に必要なものがすべて引数と自分のフィールドで閉じる。境界の前日・当日・翌日を、任意の日付で1行ずつ確かめられる。**現在時刻を取る場所は、呼び出し側の1か所に寄る。**

**判断に迷う例**: 現在時刻はどこかで取る必要がある。取る場所を無くすのではなく、判定するロジックから外へ出す。外へ出す先をどこにするかは、章「02 設計」と章「03 アーキテクチャ」が扱う。

### GC-12 テストしにくさを設計の兆候として読んでいるか

**何を見るか**: 「これはテストしにくい」と感じたとき、テストの書き方を工夫して済ませていないか。

**なぜそう言えるか**: `SRC-CODE-001` p.214（14.8）は、テストするのが難しそうだと思ったら立ち止まって設計を考え直せばよい、と述べる。同書 p.215（表14-2）は、テスト容易性の高い特性を4つ挙げる。クラスが小さいか内部状態を持たない。クラスや関数が1つのことをしている。他のクラスにあまり依存しない。関数が単純でインタフェースが明確である。

**判断に迷う例**: テストのためだけに本体コードを歪めない。`SRC-CODE-001` p.215（14.9）は、テストのために本体コードの読みやすさを犠牲にしてはならず、両者に利点がなければならないと述べる。**テスト専用の公開メソッドを足すのは、この線を越えている。**

### GC-13 カバレッジの数値目標を置いていないか

**何を見るか**: カバレッジの数値を、達成すべき目標として運用していないか。

**なぜそう言えるか**: 2つの独立した資料が、別の理由で同じ結論に達している。`SRC-CODE-001` p.215-216（14.9）は費用対効果を理由にする。最後の10%には利用者インタフェースや軽微なエラーケースが含まれ、バグのコストが高くないためテストが割に合わない。`SRC-EXT-003`（Martin Fowler「TestCoverage」）は指標のゆがみを理由にする。目標にすると、質の低いテストで数値だけを満たせてしまう。

**判断に迷う例**: カバレッジを測ること自体は有用である。`SRC-EXT-003` は、テストされていない箇所を見つける道具として使うことを勧めている。**測るのはよい。合否の線を引くのがよくない。**

## 名前の付け方

**名前の難しさは広く共有されている。** `SRC-EXT-002`（Martin Fowler「TwoHardThings」）は、Phil Karlton の言葉を引く。「コンピュータ科学で難しいのはキャッシュの無効化と名前付けの2つだけ」である。

### GC-14 名前から目的が読み取れるか

**何を見るか**: 名前が、その要素の目的や業務上の意味を示しているか。型名やコンピュータ用語をなぞっただけになっていないか。

**なぜそう言えるか**: `SRC-CODE-001` p.31（2章）は「名前に情報を詰め込む」を鍵となる考えとする。同書 p.33（2.2）は、`tmp`、`retval`、`foo` のような名前を「名前のことなんて考えていません」と言っているのと同じだとする。`SRC-CODE-002` p.232（11章）は「目的駆動名前設計」を基本の考え方として置く。**「目的駆動名前設計」は同書の著者の造語である**（同書 脚注1）。`SRC-DESIGN-001` p.18 は、対象の分野で普通に使われている業務の言葉をそのまま名前に使うと、変更が楽で安全になると述べる。

`SRC-CODE-002` p.23-24 は、悪い命名の型を2つ挙げる。型名やコンピュータ用語に由来する命名を「技術駆動命名」、`Class001` のような命名を「連番命名」と呼ぶ。どちらも意図がまったく読み取れない。**この2つの呼び名も同書の著者の造語である。**

**悪い例**

```java
public class DataManager {
    private int intFlag01;
    private List<String> list1;

    public void proc(String s) {
        if (intFlag01 == 1) {
            list1.add(s);
        }
    }

    public boolean chk() {
        return list1.size() > 0;
    }
}
```

**良い例**

```java
public class TrialSubscription {
    private SubscriptionStatus status;
    private List<String> readComicIds;

    public void recordRead(String comicId) {
        if (status == SubscriptionStatus.ACTIVE) {
            readComicIds.add(comicId);
        }
    }

    public boolean hasReadAnyComic() {
        return !readComicIds.isEmpty();
    }
}
```

**なぜ悪いのか**: `DataManager` は何のデータを管理するのかを示さず、`intFlag01` は型と連番しか伝えない。`proc` と `chk` は「処理する」「調べる」としか読めない。この名前だけでは仕様を確かめようがなく、読み手はクラス全体を読んで意味を復元する必要がある。

**なぜ良いのか**: クラス名が「お試し購読」という業務上の概念を指す。`recordRead` と `hasReadAnyComic` は、呼び出し側から見て何が起きるかを説明する。**仕様変更の依頼書に出てくる言葉と、コードの名前が一致する。**

**判断に迷う例**: 業務の言葉が英語で存在しない場合がある。そのときは、業務担当者が使う日本語の語をローマ字ではなく訳語で表す。訳語を1か所に決め、同じ概念に2つの名前を作らない。

### GC-15 名前の長さがスコープに合っているか

**何を見るか**: 名前の長さを、その名前が見えるコードの行数に合わせているか。

**なぜそう言えるか**: **この観点は、2つの資料の条件の違いを整理したものである。** `SRC-CODE-001` p.44（2.5）は、識別子が見えるコードの行数が小さければ、型・初期値・破棄方法がすべて見えるため名前は短くてよいとする。`SRC-DESIGN-001` p.17-18 は、1文字の変数名と略語を避けて意味のある単語を使えとする。**前者は条件つきの主張であり、後者は業務アプリケーションのフィールドと引数を対象にしている。** 対象が違うため、対立していない。

`SRC-EXT-004`（Google Java Style Guide）も同じ形で整理している。§5.2.6 は、公開メソッドの引数に1文字の名前を使わないとする。Google Engineering Practices（`SRC-EXT-006`）は、良い名前を次のように定義する。「その要素が何であるか・何をするかが伝わる長さがあり、かつ読みにくくなるほど長くない」。

| 名前が見える範囲 | 長さの基準 |
|---|---|
| 数行のループやブロック | 1文字から数文字でよい |
| メソッド内のローカル変数 | 目的が分かる単語1つから2つ |
| 引数・フィールド・公開メソッド | 略さない完全な単語 |

**判断に迷う例**: 略語が業務の側で定着していることがある。**業務担当者が会話で使う略語は、業務の言葉として扱ってよい**（`GC-14`）。開発者が入力の手間を減らすために作った略語は、そうではない。

### GC-16 真偽値の名前が真と偽の意味を示すか

**何を見るか**: `boolean` の変数と、`boolean` を返すメソッドの名前が、真と偽のどちらが何を意味するかを示しているか。

**なぜそう言えるか**: `SRC-CODE-001` p.55（3.6）は、真偽値の名前について2つを述べる。真と偽の意味を明確にしなければならない。頭には `is`、`has`、`can`、`should` を付けることが多い。同書は `SpaceLeft()` を数値を返すように聞こえる例として挙げ、`HasSpaceLeft()` を勧める。同書 p.55、p.60 は、否定形の名前（`disable_ssl` など）を避けるべきだとする。

**悪い例**

```java
public class Session {
    private static final long LIMIT_MILLIS = 1800000;
    private boolean disableTimeout;
    private boolean notAuthenticated;
    private String password;
    private long elapsedMillis;

    public boolean readPassword() {
        return password != null;
    }

    public boolean expired() {
        return !notAuthenticated && !disableTimeout && elapsedMillis > LIMIT_MILLIS;
    }
}
```

**良い例**

```java
public class Session {
    private static final long LIMIT_MILLIS = 1800000;
    private boolean timeoutEnabled;
    private boolean authenticated;
    private String password;
    private long elapsedMillis;

    public boolean hasPassword() {
        return password != null;
    }

    public boolean isExpired() {
        return authenticated && timeoutEnabled && elapsedMillis > LIMIT_MILLIS;
    }
}
```

**なぜ悪いのか**: `readPassword` は「パスワードを読む」という動作にも、「パスワードを読んだ」という状態にも読める。`notAuthenticated` は否定を名前に含むため、`!notAuthenticated` という二重否定が式に現れる。二重否定は読むたびに頭の中で反転が要り、読み違いを生む。

**なぜ良いのか**: `has` と `is` が、真偽値を返すことを名前で示す。名前が肯定形になったため、条件式から `!` が消えた。**式を読むだけで、どの状態のときに真になるかが分かる。**

**判断に迷う例**: `is` で始めると自然でない述語がある。そのときは `can`、`should`、`has` を検討し、それでも収まらないなら名詞句を避けて動詞句にする。**接頭辞をそろえること自体が目的ではない。真と偽の意味が分かることが目的である。**

### GC-17 範囲と定数の名前が誤解を招かないか

**何を見るか**: 範囲を表す名前が、端の値を含むかどうかを示しているか。意図の分からない数値がロジックに直接書かれていないか。

**なぜそう言えるか**: `SRC-CODE-001` p.60（3章まとめ）は、範囲を表す名前を3通りに使い分けるとする。上下の限界値には `min`／`max`、両端を含む範囲には `first`／`last`、末尾を含まない範囲には `begin`／`end` を使う。`SRC-CODE-002` p.212-213（10.3）は、ロジックに直接書かれた意図不明の数値をマジックナンバーと呼ぶ。同じ数値を複数箇所に書くと重複コードになり、仕様変更のときに修正漏れが起きる。

**悪い例**

```java
public class TrialSubscription {
    private int point;

    public boolean isOk() {
        return 60 <= point;
    }

    public void consume() {
        int tmp = point - 60;
        if (tmp < 0) {
            throw new IllegalStateException();
        }
        point = tmp;
    }

    public List<Comic> pick(List<Comic> all, int stop) {
        return all.subList(0, stop);
    }
}
```

**良い例**

```java
public class TrialSubscription {
    private static final int TRIAL_READ_COST = 60;
    private int point;

    public boolean canStartTrialRead() {
        return TRIAL_READ_COST <= point;
    }

    public void consumeForTrialRead() {
        if (point < TRIAL_READ_COST) {
            throw new IllegalStateException("お試し購読のポイントが足りない");
        }
        point -= TRIAL_READ_COST;
    }

    public List<Comic> pickUpTo(List<Comic> all, int endExclusive) {
        return all.subList(0, endExclusive);
    }
}
```

**なぜ悪いのか**: `60` が2か所に現れており、消費ポイントが50に変わったときに片方を直し忘れる。`isOk` は何が「よい」のかを示さない。`stop` という名前では、その番号の要素を含むのか含まないのかが分からず、境界の誤りを生む。

**なぜ良いのか**: `TRIAL_READ_COST` が数値に意味を与え、変更点が1か所に集まる。`endExclusive` が末尾を含まないことを名前で示す。`SRC-EXT-004`（Google Java Style Guide §5.2.4）は、定数を `UPPER_SNAKE_CASE` で書き、深く不変で観測できる副作用を持たない `static final` フィールドに限るとしている。

**判断に迷う例**: すべての数値を定数にする必要は無い。`0` や `1` のように、その場で意味が閉じている数値は残してよい。**同じ数値が2か所に現れたとき、または数値の意味を説明するコメントを書きたくなったときが、定数にする合図である。**

## Java の表記規約について

**この章の例で使った表記は、Java の表記規約に従っている。規約は原則ではない。**

| 種類 | 表記 |
|---|---|
| クラス | `UpperCamelCase` の名詞句 |
| メソッド | `lowerCamelCase` の動詞句 |
| 定数 | `UPPER_SNAKE_CASE` |
| フィールド・引数・ローカル変数 | `lowerCamelCase` |
| 頭字語 | 1語として扱う（`XmlHttpRequest`） |

出所は `SRC-EXT-004`（Google Java Style Guide §5）である。**これは規格でも標準化団体の文書でもなく、Google が公開している社内標準である。** 表記規約は言語ごとに違うため、この手引きの原則としては扱わない。使っている言語の規約が別にあるなら、そちらに従う。

**真偽値の接頭辞（`is`、`has`、`can`、`should`）だけは扱いが違う。** これは書籍の一次資料（`SRC-CODE-001` p.55）が独立に支持しており、表記の問題ではなく意味の問題である。観点 `GC-16` として扱う。

## 決着していないこと

**次の1点は、調査の段階で決着しなかった。決着したように書かない。**

ISO/IEC 25010 の規格本体を読めていない。`www.iso.org` の該当ページと ISO Online Browsing Platform が、2026-09-07 の時点でどちらも HTTP 403 を返した。そのため、保守性の副特性の定義を規格で確認できていない。副特性は5つあるとされる。モジュール性、再利用性、解析性、修正性、試験性である。

**この章は、規格そのものを主張の根拠にしていない。** 「良いコードとは変更容易性が高いコードである」という趣旨は `SRC-CODE-002` p.343（書籍の本文）を出典としている。同書はその記述を JIS X 25010:2013 を参考に作ったと明記している。**規格を根拠に使ってよいかは決着していない。** 決着させるには、規格本体か JIS の本体を読む必要がある。読んだ時点で、この節を書き換える。
